Get started with peabiru

peabiru computes travel times and accessibility on transport networks built from an OpenStreetMap extract and GTFS public transport feeds, by walking, cycling, driving and public transport. The routing engine is written in Rust and runs inside the R session: no Java is needed, and the network is built once, in memory.

This vignette runs on the small network that ships with the package: the streets around Avenida Paulista in São Paulo, the city’s frequency-based bus and metro feed, and 27 points of a hexagonal grid. Every chunk below runs in a fraction of a second.

library(peabiru)

Build a network

A network is built from a directory holding one .pbf file and any number of GTFS .zip files. It lives in memory and is reused by every routing call.

list.files(data_path)
#> [1] "spo_gtfs.zip"   "spo_osm.pbf"    "spo_points.csv"

Travel times on the street network

travel_time_matrix() with one street mode gives the travel time in whole minutes from every origin to every destination; pairs that cannot be reached within max_trip_duration (120 minutes by default) are left out.

walk <- travel_time_matrix(network, points, points, mode = "WALK",
                           n_threads = 2)

The results are tibbles. options(peabiru.output = "data.frame") makes every function return base data frames instead, and options(peabiru.output = "data.table") data.tables; the rows, columns and values are the same whatever the class. The article “peabiru with sf and the tidyverse” goes from points to maps with sf, dplyr and ggplot2.

Walking is at walk_speed (3.6 km/h by default). Cycling is at bike_speed on streets whose level of traffic stress is at most max_lts; elsewhere the cyclist walks the bike. Driving uses each street’s speed, turn costs and turn restrictions.

Travel times by public transport

With mode = c("WALK", "TRANSIT") the trip combines walking and public transport. A departure time is needed, and the result summarises the trips that leave in each minute of time_window as percentiles. This feed is frequency-based, so the departures are simulated with random draws: give a seed to make them reproducible.

departure <- as.POSIXct("2019-05-13 14:00:00", tz = "America/Sao_Paulo")

ttm <- travel_time_matrix(
  network, points, points,
  mode = c("WALK", "TRANSIT"),
  departure_datetime = departure,
  time_window = 10,
  percentiles = c(25, 50, 75),
  seed = 42,
  n_threads = 2
)
head(ttm)

Walking all the way is one of the options considered, so here adding public transport never makes a trip longer; on this small network it shortens many of the longer ones:

both <- merge(walk, ttm, by = c("from_id", "to_id"),
              suffixes = c("_walk", "_transit"))
mean(both$travel_time_p50_transit < both$travel_time_p50_walk)
#> [1] 0.3731139

     xlab = "walking (min)", ylab = "walk + transit, median (min)",
     pch = 16, col = "#b4532a80", asp = 1)
abline(0, 1, col = "grey50")

Accessibility

accessibility() counts the opportunities each origin can reach. With the "step" function and two cutoffs, the result is the number of jobs within 15 and within 30 minutes:

access <- accessibility(
  network, points, points,
  opportunities_colnames = "jobs",
  mode = c("WALK", "TRANSIT"),
  departure_datetime = departure,
  decay_function = "step",
  cutoffs = c(15, 30),
  seed = 42,
  n_threads = 2
)
head(access)

Trip by trip

expanded_travel_time_matrix() keeps every trip instead of a percentile: one row per departure minute and, with a frequency-based feed, per draw. With breakdown = TRUE each trip is split into its access walk, waiting, riding, transfers and egress walk, with the routes taken.

trips <- expanded_travel_time_matrix(
  network, points[1, ], points,
  mode = c("WALK", "TRANSIT"),
  departure_datetime = departure,
  time_window = 2,
  breakdown = TRUE,
  seed = 42,
  n_threads = 2
)

arrival_travel_time_matrix() answers the reverse question: for each pair, the latest departure that still arrives by a given time.

Writing results to files

For matrices too large to hold in memory, output_dir (an existing directory) makes each of these functions write its result there instead of returning it: one CSV file per origin, from_<id>.csv. The origins are routed a slice at a time, and the function returns output_dir.

out <- tempfile("peabiru-")
dir.create(out)
travel_time_matrix(network, points, points, mode = "CAR", n_threads = 2,
                   output_dir = out) == out
#> [1] TRUE
length(list.files(out))
#> [1] 27
head(read.csv(file.path(out, list.files(out)[1])), 3)
#>           from_id           to_id travel_time_p50
#> 1 89a8100c007ffff 89a8100c00fffff               4
#> 2 89a8100c007ffff 89a8100c007ffff               1

More

The package also computes isochrones (isochrone()), the legs of each trip (detailed_itineraries()), fares (setup_fare_structure(), pareto_frontier()), slope costs from an elevation raster, and scenarios of car speeds and traffic stress; it inspects networks with find_snap(), street_network_to_sf(), transit_network_to_sf(), check_transit_availability() and get_gtfs_errors(). The articles on the package website show each of them.

What peabiru does not support is an error that says so, never ignored or approximated: for instance a fare structure that names a fare calculator (a type) instead of fare rules:

fares <- setup_fare_structure(network, base_fare = 4.4)
fares$type <- "burlington"
travel_time_matrix(network, points, points, mode = c("WALK", "TRANSIT"),
                   departure_datetime = departure, fare_structure = fares)
#> Error:
#> ! A fare structure with a 'type' (a named fare calculator instead of fare rules) is not supported by peabiru.

The help page of each function lists its arguments and their defaults.
