peabiru for JavaScript

Detailed itineraries

detailedItineraries() gives the legs of each trip between pairs of origins and destinations: each walk, ride by bicycle or car, and each public transport ride, with its duration, waiting time, distance, route and line.

The examples on this page use the sample data of Porto Alegre from the r5r project, whose GTFS feeds have timetables (itineraries by public transport need them: a network with frequency-based trips is an error) and only have service in the afternoon, hence the 14:00 departure. The files are downloaded once into the temporary directory (about 2 MB) by a small helper:

const POA = "https://raw.githubusercontent.com/ipea/r5r/v2.5.0/r-package/inst/extdata/poa/";

/** The bytes of a file of the Porto Alegre sample, downloaded the first time. */
export async function poaFile(name) {
  const dir = join(tmpdir(), "peabiru-poa");
  const path = join(dir, name);
  if (!existsSync(path)) {
    const response = await fetch(POA + name);
    if (!response.ok) throw new Error(`${POA + name}: HTTP ${response.status}`);
    mkdirSync(dirname(path), { recursive: true });
    writeFileSync(`${path}.part`, new Uint8Array(await response.arrayBuffer()));
    renameSync(`${path}.part`, path);
  }
  return readFile(path);
}

// the feeds in the order macOS lists the sample directory
const network = await peabiru.buildNetwork({
  pbf: await poaFile("poa_osm.pbf"),
  gtfs: [
    { name: "poa_trensurb.zip", data: await poaFile("poa_trensurb.zip") },
    { name: "poa_eptc.zip", data: await poaFile("poa_eptc.zip") },
  ],
});
const points = parsePoints((await poaFile("poa_points_of_interest.csv")).toString());
const pick = (...k) => ({ id: k.map((i) => points.id[i]), lon: k.map((i) => points.lon[i]), lat: k.map((i) => points.lat[i]) });

The fastest trip

Origins and destinations are paired row by row (a single origin or destination is repeated to match the other, with a warning). Each pair gets its fastest itinerary (shortestPath: true, the default): the trip by the street mode alone, or the fastest public transport trip over the departure window (departureDatetime and the timeWindow minutes after it), whichever is faster. Pairs without an itinerary have no rows.

// paired row by row: the first origin with the first destination, and so on
const origins = pick(0, 1, 2);
const destinations = pick(3, 4, 5);
const trips = await peabiru.detailedItineraries(network, origins, destinations, {
  mode: ["WALK", "TRANSIT"],
  departureDatetime: "2019-05-13 14:00:00",
});
console.log(trips.type, trips.features.length, "legs");
const legs = trips.features.map((f) => f.properties);
show(legs, ["from_id", "to_id", "option", "departure_time", "total_duration", "segment", "mode", "segment_duration", "wait", "distance", "route"]);
const line = trips.features[2].geometry;
console.log(line.type, line.coordinates.length, "points, from", line.coordinates[0]);

The result is a GeoJSON FeatureCollection with one LineString feature per leg (coordinates [lon, lat], WGS 84); the properties are the row’s columns. With dropGeometry: true it is an array of the rows themselves. The columns:

Column
from_id, from_lat, from_lon, to_id, to_lat, to_lonthe pair
optionthe itinerary, from 1
departure_time"HH:MM:SS", when the itinerary leaves the origin
total_duration, total_distanceof the itinerary: minutes (one decimal), metres
total_farewith a fareStructure only
segmentthe leg, from 1
mode"WALK", "BICYCLE", "CAR", or the ride’s mode ("BUS", "RAIL", …)
cumulative_farewith a fareStructure only: what was paid up to the end of the leg
segment_duration, wait, distanceof the leg: minutes, minutes, metres
routethe GTFS route_id of a ride; empty for a street leg
osm_id_list, edge_id_list, board_stop_id, alight_stop_idwith osmLinkIds: true only (see below)

How the lines are drawn:

  • a street leg’s line holds the whole of its first and last street segments, not only the parts walked or driven; the leg from the last stop ends at the destination itself;
  • a ride follows the GTFS shape of its trip pattern, or straight lines between its stops when the feed has no shapes;
  • a walk between stops is routed again on the streets for its line and distance; its duration is the one the public transport search used.

Alternatives

With shortestPath: false the result lists the itineraries the multi-criteria router (McRAPTOR) keeps over the departure window, one per sequence of routes, with the trip by the street mode alone first:

const alternatives = (suboptimalMinutes) =>
  peabiru.detailedItineraries(network, pick(1), pick(4), {
    mode: ["WALK", "TRANSIT"],
    departureDatetime: "2019-05-13 14:00:00",
    shortestPath: false, // McRAPTOR's alternatives, one per sequence of routes
    suboptimalMinutes,
    dropGeometry: true, // plain rows, no GeoJSON
  });
const options = await alternatives(0);
for (const rows of byOption(options)) {
  console.log(`option ${rows[0].option}: ${rows[0].departure_time}, ${rows[0].total_duration} min, ${via(rows)}`);
}
const wider = await alternatives(3);
console.log(`with suboptimalMinutes: 3, ${new Set(wider.map((r) => r.option)).size} options`);

suboptimalMinutes widens the search: at every stop, McRAPTOR also keeps the states that arrive up to that many minutes after the best one there, so more sequences of routes survive. It does not cap an alternative’s duration at the best plus suboptimalMinutes, since each departure minute of the window is searched on its own. It must be 0 with shortestPath: true and with a fareStructure.

The options are numbered in this order: the trip by the street mode alone first, then by the number of legs, then by duration. The first option is then not the fastest when a trip with fewer legs is slower (on Porto Alegre with suboptimalMinutes: 10, a pair had 102 options, the first of 60.4 minutes and the fastest of 53.3).

Every origin to every destination

allToAll: true routes every origin to every destination instead of pairing them:

const all = await peabiru.detailedItineraries(network, pick(0, 1), pick(3, 4, 5), {
  mode: "BICYCLE",
  departureDatetime: "2019-05-13 14:00:00",
  allToAll: true, // 2 origins x 3 destinations
  dropGeometry: true,
});
show(all, ["from_id", "to_id", "mode", "total_duration", "total_distance"]);

The OpenStreetMap ways of a leg

osmLinkIds: true (which needs the geometry, so not with dropGeometry) adds four properties: osm_id_list, the OpenStreetMap way ids of a street leg’s edges, and edge_id_list, the indices of those edges in the network (the edge_index of streetNetworkToSf()), both as text "[id1, id2, ...]" ("[]" for a ride; consecutive edges on a roundabout give only their first ids, and the connectors to stops none); and, for a ride, board_stop_id and alight_stop_id, "<feed id>:<stop_id>" (empty for street legs).

const walk = await peabiru.detailedItineraries(network, pick(0), pick(3), {
  mode: "WALK",
  departureDatetime: "2019-05-13 14:00:00",
  osmLinkIds: true, // needs the geometry
});
const leg = walk.features[0].properties;
console.log("OpenStreetMap ways:", leg.osm_id_list);
console.log("street edges:", leg.edge_id_list);

Fares

With a fare structure, trips are routed with fares (only those up to maxFare, Infinity by default) and the rows get total_fare and cumulative_fare:

const fares = await peabiru.setupFareStructure(network, 4.8); // every ride 4.80, a transfer too
const priced = await peabiru.detailedItineraries(network, pick(1), pick(4), {
  mode: ["WALK", "TRANSIT"],
  departureDatetime: "2019-05-13 14:00:00",
  fareStructure: fares,
  shortestPath: false,
  dropGeometry: true,
});
for (const rows of byOption(priced)) {
  const paid = rows.map((r) => r.cumulative_fare).join(", ");
  console.log(`option ${rows[0].option}: ${rows[0].total_duration} min, fare ${rows[0].total_fare} (${via(rows)}; paid after each leg: ${paid})`);
}

Car egress and turn restrictions

With modeEgress: "CAR", the egress is searched backwards from the destination, and a turn restriction with two or more via ways can be read in either order of those ways. peabiru fixes the order: every pair gets the itineraries of a freshly built network routing that pair alone with one thread, whatever the other pairs, the threads or the earlier calls, and a warning, once per call (onWarning), names the pairs whose itineraries the other order of those via ways would change (on Porto Alegre, about 1 pair in 200). Rides along GTFS shapes are cut by shape_dist_traveled where the feed has it.

The trips for which the fastest-path search cannot rebuild a path are routed again with McRAPTOR.
