1//! Multimodal routing engine behind the `peabiru` packages for R, Python and
2//! JavaScript.
3//!
4//! The engine builds a routable [`Network`] in memory from an OpenStreetMap
5//! PBF extract (walk, bike, car), optionally GTFS feeds (public transport)
6//! and an elevation raster, and computes over it:
7//!
8//! - travel-time matrices by street ([`street_travel_time_matrix`]) and by
9//!   public transport ([`transit_travel_time_matrix`]: any subset of the
10//!   transit modes, reached and left on foot, by bicycle or by car), with
11//!   percentiles and Monte Carlo draws for frequency-based feeds;
12//! - accessibility with five decay functions ([`transit_accessibility`],
13//!   [`street_accessibility`]);
14//! - expanded and arrival-time matrices ([`expanded_travel_time_matrix`],
15//!   [`arrival_travel_time_matrix`]);
16//! - isochrones, as polygons or street segments (see [Isochrones](#isochrones));
17//! - detailed itineraries, leg by leg ([`detailed_itineraries`]);
18//! - fares: travel times within a budget, fares of itineraries and the
19//!   Pareto frontier of time and fare (see [Fares](#fares));
20//! - slope costs for walking and cycling from a GeoTIFF raster ([`Elevation`]);
21//! - scenarios of car speeds and levels of traffic stress ([`Scenario`]);
22//! - facility location on a table of travel times: maximal covering, set
23//!   covering, p-median and p-center ([`locate_facilities`]), and the
24//!   two-step floating catchment area ([`floating_catchment`]);
25//! - what a network holds, and the GTFS errors of each feed (see
26//!   [Inspecting a network](#inspecting-a-network)).
27//!
28//! This crate is the shared core: the R package (extendr), the Python
29//! package (PyO3) and the JavaScript package (wasm-bindgen) are thin
30//! bindings over the same functions, so they all return the same numbers;
31//! the `peabiru` command-line tool runs it on CSV files.
32//!
33//! # Example
34//!
35//! Build a network from a directory holding one OpenStreetMap `.pbf` and
36//! the GTFS `.zip` feeds, then compute a street and a public transport
37//! matrix between the same points:
38//!
39//! ```no_run
40//! use peabiru_core::{
41//!     build_from_dir, street_travel_time_matrix, transit_travel_time_matrix, BuildOptions,
42//!     Mode, RouteParams, TransitParams,
43//! };
44//!
45//! # fn main() -> Result<(), Box<dyn std::error::Error>> {
46//! // the São Paulo sample of the repository (r/inst/extdata/spo)
47//! let network = build_from_dir("r/inst/extdata/spo", &BuildOptions::default())?;
48//! for w in network.build_warnings() {
49//!     eprintln!("warning: {w}");
50//! }
51//! let points = [(-23.5563, -46.6290), (-23.5577, -46.6321)]; // (lat, lon)
52//!
53//! // walking, with the default parameters
54//! let walk = street_travel_time_matrix(&network, &points, &points, Mode::Walk, &RouteParams::default())?;
55//! println!("walk: {:?} min", walk.get(0, 1));
56//!
57//! // walking and public transport, Monday 2019-05-13 from 14:00
58//! let mut params = TransitParams::default();
59//! params.date = 20190513;
60//! params.departure_time = 14 * 3600;
61//! params.seed = Some(42);
62//! let transit = transit_travel_time_matrix(&network, &points, &points, &params)?;
63//! println!("transit: {:?} min at percentiles {:?}", transit.get(0, 1), transit.percentiles());
64//! # Ok(())
65//! # }
66//! ```
67//!
68//! A [`Network`] is built once and shared by every call (and by threads):
69//! every function takes it whole, so the streets and the public transport
70//! layer linked to them always go together.
71//!
72//! [`build_from_bytes`] builds the same network from data held in memory
73//! (the `.pbf` and the feeds' `.zip` files as bytes), for callers without
74//! a file system, such as the JavaScript package on WebAssembly.
75//!
76//! # Threads
77//!
78//! Each parameter struct has an `n_threads` field: the work is shared out
79//! among that many worker threads (0 = all cores), and the results never
80//! depend on it. On WebAssembly targets, where `std` cannot start threads,
81//! everything runs on the calling thread whatever `n_threads` says.
82//!
83//! # Parameters
84//!
85//! Every parameter struct ([`BuildOptions`], [`RouteParams`],
86//! [`TransitParams`], [`AccessibilityParams`], [`ItineraryParams`],
87//! [`LocationParams`], [`FloatingCatchmentParams`]) starts
88//! from `Default` ([`BuildOptions::elevation`] is off by default) and is
89//! filled in by setting its public fields:
90//!
91//! ```
92//! let mut p = peabiru_core::RouteParams::default();
93//! p.walk_speed = 4.5;
94//! p.max_trip_duration = 60;
95//! ```
96//!
97//! The structs are `#[non_exhaustive]`, so later versions can add fields
98//! without breaking this code; for the same reason they cannot be written
99//! as struct expressions outside this crate, not even with
100//! `..Default::default()`. Invalid values are rejected with
101//! [`RouteError::Invalid`] before any routing.
102//!
103//! # Isochrones
104//!
105//! Polygon isochrones take two calls: a travel-time surface to the cells of
106//! a Web Mercator grid ([`street_travel_time_surface`],
107//! [`transit_travel_time_surface`]), then [`isochrone_polygons`] on it.
108//! Line isochrones route a matrix to the centroids of [`street_edges`] and
109//! band it with [`isochrone_lines`]. The functions say what they return and
110//! what is left to the caller (repairing and clipping the polygons).
111//!
112//! # Inspecting a network
113//!
114//! What a network holds: where points snap to the streets
115//! ([`find_snap`]), the box of the street network
116//! ([`Network::street`], [`StreetNetwork::bbox`]), its vertices and edges ([`street_vertices`],
117//! [`street_edges`]), the transit stops and the routes of each trip
118//! pattern ([`transit_stops`], [`transit_routes`]), the dates with service
119//! ([`transit_service_dates`], [`TransitLayer::n_services_active_on`]) and
120//! the errors gtfs-lib reports loading a feed ([`gtfs_errors`]).
121//!
122//! A network is not built from a feed with GTFS errors of priority `HIGH`,
123//! or from one gtfs-lib cannot load: the build fails, and
124//! [`NetworkError::high_priority_gtfs_errors`] names the feeds. With
125//! [`BuildOptions::ignore_gtfs_errors`] it is built from what can be read,
126//! and [`Network::build_warnings`] says which feeds those are (with the
127//! warnings about the elevation raster).
128//!
129//! # Itineraries
130//!
131//! [`detailed_itineraries`] routes each origin to the destination of the
132//! same index and returns the trips leg by leg ([`Itinerary`],
133//! [`ItineraryLeg`]), with their lines: by a street mode, or with public
134//! transport the fastest trip over the departure window or, with
135//! [`ItineraryParams::shortest_path`] `false`, the alternatives of the
136//! multi-criteria router. Networks with frequency-based trips are refused
137//! there. [`write_itineraries_csv`] writes them to CSV files.
138//!
139//! # Fares
140//!
141//! A [`FareStructure`] ([`setup_fare_structure`], [`read_fare_structure`],
142//! [`write_fare_structure`]) in [`TransitParams::fare_structure`] routes
143//! public transport with the multi-criteria router and fares; with
144//! [`TransitParams::max_fare`] the matrices and accessibility keep the
145//! fastest trip within the budget. [`pareto_frontier`] gives, per
146//! destination, the travel time at each fare cutoff where it changes, and
147//! [`ItineraryParams::fare_structure`] the fares of itineraries.
148//!
149//! # Elevation
150//!
151//! With [`BuildOptions::elevation`] set to [`Elevation::Tobler`] or
152//! [`Elevation::Minetti`], walking and cycling times depend on the slope of
153//! each street, from the `.tif` raster of the directory
154//! ([`build_from_dir`]) or from its bytes
155//! ([`build_from_bytes_with_elevation`], which lists the rasters and
156//! coordinate systems supported). [`StreetNetwork::elevation_warnings`]
157//! reports voids, out-of-range values and samples on a pixel boundary.
158//!
159//! # Results
160//!
161//! A matrix is returned in a type of its own ([`StreetMatrix`],
162//! [`TransitMatrix`], [`ExpandedMatrix`], [`Accessibility`]), which gives
163//! its dimensions, single values, rows, and its whole buffer without
164//! copying (`into_vec`, `into_values`). [`CsvOutput`] writes them to one
165//! CSV file per origin, formatted as `data.table::fwrite` formats them.
166//!
167//! # Scenarios
168//!
169//! [`RouteParams::scenario`], [`TransitParams::scenario`] and
170//! [`ItineraryParams::scenario`] change the car speeds and the levels of
171//! traffic stress of the streets for one call (see [`Scenario`]); the
172//! network itself is left as it is.
173//!
174//! # Facility location
175//!
176//! [`locate_facilities`] chooses where to open facilities, by one of four
177//! models ([`LocationModel`]), and [`floating_catchment`] compares supply
178//! with demand around each place. Both work on a [`CostTable`], the minutes
179//! from each demand point to each site, whatever computed it:
180//! [`CostTable::from_minutes`] takes the minutes of a matrix of this crate.
181//! The models are solved by heuristics (greedy construction, then vertex
182//! substitution), deterministically and with no dependency.
183//!
184//! # Cancellation
185//!
186//! Every routing parameter struct holds a [`CancelToken`]: cancel a clone
187//! of it from another thread and the computation returns
188//! [`RouteError::Cancelled`].
189//!
190//! # Routing model and credits
191//!
192//! The routing model follows that of Conveyal's
193//! [R5](https://github.com/conveyal/r5) (MIT), from which the routing logic
194//! is ported; the repository checks the results against reference outputs
195//! (see the [comparison with r5r](https://strategicprojects.github.io/peabiru-routing/rust/parity.html)).
196//! The few places where results depend on the platform
197//! (the order in which the operating system lists GTFS feeds, the C++
198//! library isoband was built with) are documented with the functions
199//! concerned.
200//!
201//! Polygon isochrones are a translation of the isoband algorithm (MIT);
202//! parts of Apache Commons Math 3.0 (Apache-2.0) and fdlibm 5.3 are
203//! translated, so that the numbers are the same on every platform. The
204//! notices of these and of
205//! the other works the crate derives from are in `LICENSE-THIRD-PARTY`.

340    /// One directed edge of a street network, as stored.
341    #[derive(Debug, Clone, Copy)]
342    pub struct Edge {
343        /// OSM way id (negative for a generated connector).
344        pub way: i64,
345        /// Length in millimetres.
346        pub length_mm: i32,
347        /// Bit set of [`flags`].
348        pub flags: u32,
349        /// Car speed in cm/s, as stored.
350        pub speed_cms: i16,
351        /// Start and end vertex as `(lat, lon)`, fixed-point 1e-7 degrees.
352        pub from: (i32, i32),
353        pub to: (i32, i32),
354    }

356    /// The elevations R5 would sample on `net` from a GeoTIFF raster, in
357    /// decimetres: one per vertex, and per edge pair the points every
358    /// 10 m inside it (for comparing with R5's `ElevationCostField`).
359    pub fn elevation_samples(
360        net: &StreetNetwork,
361        raster: &[u8],
362    ) -> Result<(Vec<i16>, Vec<Vec<i16>>), String> {
363        crate::elevation::samples_of(net, raster).map(|s| (s.vertex_dm, s.profile_dm))
364    }

366    /// A sample of [`raster_samples`]: the value read and whether the point
367    /// is ambiguous (within nanometres of a pixel boundary, where R5's
368    /// pixel depends on the machine), or why R5 fails there.
369    pub type RasterSample = Result<(f64, bool), String>;
370
371    /// R5's `RasterDataSourceSampler.readElevation` on a GeoTIFF raster, for
372    /// each `(lon, lat)`: the value of the nearest pixel, 0 outside the
373    /// raster (as Java's StrictMath places the point), or why R5 (or this
374    /// reader) fails there. An error for a raster that cannot be read.
375    pub fn raster_samples(
376        raster: &[u8],
377        points: &[(f64, f64)],
378    ) -> Result<Vec<RasterSample>, String> {
379        crate::elevation::read_points(raster, points)
380    }
381
382    /// The transform R5 (GeoTools) applies to WGS 84 `(lon, lat)` points
383    /// for a raster in EPSG `code`, `None` for a system peabiru does not
384    /// support (for comparing with GeoTools).
385    pub fn crs_transform(code: u32, points: &[(f64, f64)]) -> Option<Vec<(f64, f64)>> {
386        let c = crate::elevation::crs::lookup(code)?;
387        Some(points.iter().map(|&(lon, lat)| c.apply(lon, lat)).collect())
388    }
389
390    /// The slope factor of directed edge `e` (`None` without elevation).
391    pub fn edge_slope(net: &StreetNetwork, e: usize) -> Option<f32> {
392        net.edge_slope.get(e).copied()
393    }
394
395    /// Directed edge `e` of `net` (`0..net.n_edges()`).
396    pub fn edge(net: &StreetNetwork, e: usize) -> Edge {
397        let (v0, v1) = (net.edge_from(e), net.edge_to(e));
398        Edge {
399            way: net.pair_way[e / 2],
400            length_mm: net.pair_length_mm[e / 2],
401            flags: net.edge_flags[e],
402            speed_cms: net.edge_speed_cms[e],
403            from: (net.v_lat[v0], net.v_lon[v0]),
404            to: (net.v_lat[v1], net.v_lon[v1]),
405        }
406    }
