Crate peabiru_core 

Source
Expand description

Multimodal routing engine behind the peabiru packages for R, Python and JavaScript.

The engine builds a routable Network in memory from an OpenStreetMap PBF extract (walk, bike, car), optionally GTFS feeds (public transport) and an elevation raster, and computes over it:

  • travel-time matrices by street (street_travel_time_matrix) and by public transport (transit_travel_time_matrix: any subset of the transit modes, reached and left on foot, by bicycle or by car), with percentiles and Monte Carlo draws for frequency-based feeds;
  • accessibility with five decay functions (transit_accessibility, street_accessibility);
  • expanded and arrival-time matrices (expanded_travel_time_matrix, arrival_travel_time_matrix);
  • isochrones, as polygons or street segments (see Isochrones);
  • detailed itineraries, leg by leg (detailed_itineraries);
  • fares: travel times within a budget, fares of itineraries and the Pareto frontier of time and fare (see Fares);
  • slope costs for walking and cycling from a GeoTIFF raster (Elevation);
  • scenarios of car speeds and levels of traffic stress (Scenario);
  • facility location on a table of travel times: maximal covering, set covering, p-median and p-center (locate_facilities), and the two-step floating catchment area (floating_catchment);
  • what a network holds, and the GTFS errors of each feed (see Inspecting a network).

This crate is the shared core: the R package (extendr), the Python package (PyO3) and the JavaScript package (wasm-bindgen) are thin bindings over the same functions, so they all return the same numbers; the peabiru command-line tool runs it on CSV files.

§Example

Build a network from a directory holding one OpenStreetMap .pbf and the GTFS .zip feeds, then compute a street and a public transport matrix between the same points:

use peabiru_core::{
    build_from_dir, street_travel_time_matrix, transit_travel_time_matrix, BuildOptions,
    Mode, RouteParams, TransitParams,
};

// the São Paulo sample of the repository (r/inst/extdata/spo)
let network = build_from_dir("r/inst/extdata/spo", &BuildOptions::default())?;
for w in network.build_warnings() {
    eprintln!("warning: {w}");
}
let points = [(-23.5563, -46.6290), (-23.5577, -46.6321)]; // (lat, lon)

// walking, with the default parameters
let walk = street_travel_time_matrix(&network, &points, &points, Mode::Walk, &RouteParams::default())?;
println!("walk: {:?} min", walk.get(0, 1));

// walking and public transport, Monday 2019-05-13 from 14:00
let mut params = TransitParams::default();
params.date = 20190513;
params.departure_time = 14 * 3600;
params.seed = Some(42);
let transit = transit_travel_time_matrix(&network, &points, &points, &params)?;
println!("transit: {:?} min at percentiles {:?}", transit.get(0, 1), transit.percentiles());

A Network is built once and shared by every call (and by threads): every function takes it whole, so the streets and the public transport layer linked to them always go together.

build_from_bytes builds the same network from data held in memory (the .pbf and the feeds’ .zip files as bytes), for callers without a file system, such as the JavaScript package on WebAssembly.

§Threads

Each parameter struct has an n_threads field: the work is shared out among that many worker threads (0 = all cores), and the results never depend on it. On WebAssembly targets, where std cannot start threads, everything runs on the calling thread whatever n_threads says.

§Parameters

Every parameter struct (BuildOptions, RouteParams, TransitParams, AccessibilityParams, ItineraryParams, LocationParams, FloatingCatchmentParams) starts from Default (BuildOptions::elevation is off by default) and is filled in by setting its public fields:

let mut p = peabiru_core::RouteParams::default();
p.walk_speed = 4.5;
p.max_trip_duration = 60;

The structs are #[non_exhaustive], so later versions can add fields without breaking this code; for the same reason they cannot be written as struct expressions outside this crate, not even with ..Default::default(). Invalid values are rejected with RouteError::Invalid before any routing.

§Isochrones

Polygon isochrones take two calls: a travel-time surface to the cells of a Web Mercator grid (street_travel_time_surface, transit_travel_time_surface), then isochrone_polygons on it. Line isochrones route a matrix to the centroids of street_edges and band it with isochrone_lines. The functions say what they return and what is left to the caller (repairing and clipping the polygons).

§Inspecting a network

What a network holds: where points snap to the streets (find_snap), the box of the street network (Network::street, StreetNetwork::bbox), its vertices and edges (street_vertices, street_edges), the transit stops and the routes of each trip pattern (transit_stops, transit_routes), the dates with service (transit_service_dates, TransitLayer::n_services_active_on) and the errors gtfs-lib reports loading a feed (gtfs_errors).

A network is not built from a feed with GTFS errors of priority HIGH, or from one gtfs-lib cannot load: the build fails, and NetworkError::high_priority_gtfs_errors names the feeds. With BuildOptions::ignore_gtfs_errors it is built from what can be read, and Network::build_warnings says which feeds those are (with the warnings about the elevation raster).

§Itineraries

detailed_itineraries routes each origin to the destination of the same index and returns the trips leg by leg (Itinerary, ItineraryLeg), with their lines: by a street mode, or with public transport the fastest trip over the departure window or, with ItineraryParams::shortest_path false, the alternatives of the multi-criteria router. Networks with frequency-based trips are refused there. write_itineraries_csv writes them to CSV files.

§Fares

A FareStructure (setup_fare_structure, read_fare_structure, write_fare_structure) in TransitParams::fare_structure routes public transport with the multi-criteria router and fares; with TransitParams::max_fare the matrices and accessibility keep the fastest trip within the budget. pareto_frontier gives, per destination, the travel time at each fare cutoff where it changes, and ItineraryParams::fare_structure the fares of itineraries.

§Elevation

With BuildOptions::elevation set to Elevation::Tobler or Elevation::Minetti, walking and cycling times depend on the slope of each street, from the .tif raster of the directory (build_from_dir) or from its bytes (build_from_bytes_with_elevation, which lists the rasters and coordinate systems supported). StreetNetwork::elevation_warnings reports voids, out-of-range values and samples on a pixel boundary.

§Results

A matrix is returned in a type of its own (StreetMatrix, TransitMatrix, ExpandedMatrix, Accessibility), which gives its dimensions, single values, rows, and its whole buffer without copying (into_vec, into_values). CsvOutput writes them to one CSV file per origin, formatted as data.table::fwrite formats them.

§Scenarios

RouteParams::scenario, TransitParams::scenario and ItineraryParams::scenario change the car speeds and the levels of traffic stress of the streets for one call (see Scenario); the network itself is left as it is.

§Facility location

locate_facilities chooses where to open facilities, by one of four models (LocationModel), and floating_catchment compares supply with demand around each place. Both work on a CostTable, the minutes from each demand point to each site, whatever computed it: CostTable::from_minutes takes the minutes of a matrix of this crate. The models are solved by heuristics (greedy construction, then vertex substitution), deterministically and with no dependency.

§Cancellation

Every routing parameter struct holds a CancelToken: cancel a clone of it from another thread and the computation returns RouteError::Cancelled.

§Routing model and credits

The routing model follows that of Conveyal’s R5 (MIT), from which the routing logic is ported; the repository checks the results against reference outputs (see the comparison with r5r). The few places where results depend on the platform (the order in which the operating system lists GTFS feeds, the C++ library isoband was built with) are documented with the functions concerned.

Polygon isochrones are a translation of the isoband algorithm (MIT); parts of Apache Commons Math 3.0 (Apache-2.0) and fdlibm 5.3 are translated, so that the numbers are the same on every platform. The notices of these and of the other works the crate derives from are in LICENSE-THIRD-PARTY.

write_trip_options_csv
Write trip_options’ result to dir, one file per pair with options, <dir>/from_<origin id>_to_<destination id>.csv: one row per leg of each option (with TripOptionsParams::itineraries) or per option, with the pair’s ids and points, the option’s columns (option, total_time, fare with a fare structure, transfers, walk_time, departure_time, arrival_time, n_departures, first_departure, last_departure, description) and the leg’s (segment, mode, cumulative_fare with a fare structure, segment_duration, wait, distance, route, the four id columns with osm_link_ids, and the geometry as WKT unless drop_geometry). Numbers are written as in the files of CsvOutput. ids and points are those of the pairs given to trip_options.
